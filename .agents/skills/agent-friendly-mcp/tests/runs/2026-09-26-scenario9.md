## Critical

### C1. All four rules sit after the likely truncation point, so Claude Code probably never shows them to the model
- **Where:** `instructions`. `Rules:` starts at char 2,208 and the last rule ends at 2,736. With a ~2,048-char prefix, the text is cut mid-sentence inside the `request_id` explanation, around offset 2,000–2,048 ("…correlates the failure with server logs and should b").
- **What gets lost:** every binding rule. That covers resolving `project_id` through `ledgerline_list_projects`, the dry-run → `confirm_token` flow for the irreversible void, the closed-period ban, and the rate limit.
- **What survives:** about 1,300 characters of company history and use-case background, plus most of a field-by-field error reference.
- **Consequence:** on the one client where truncation is known to happen, the model sees only the parts the server doesn't need it to see.
- **Remediation:**
  1. Put the rules first. The string should open with them.
  2. Keep the whole string well under the cap. Aim for about 1,000 characters so that even a smaller limit, or future growth, keeps every rule.
  3. Drop the history paragraph completely. Cut the error reference down to one rule (see H4).
  4. Suggested replacement, about 700 characters:

```
Ledgerline: read and post journal entries in accountants' client ledgers. Does not file taxes, move money, connect banks, or send invoices.
Rules:
- Get project_id from ledgerline_list_projects; names repeat across fiscal years and are never accepted as identifiers.
- Voiding is irreversible: call ledgerline_void_entry with dry_run=true, show the preview to the accountant, then call again with the returned confirm_token within 5 minutes.
- Do not post or void into a closed period (period_status from ledgerline_list_projects). On period_closed, stop and tell the accountant; do not retry.
- On any error, branch on error.code, follow error.repair when present, and retry only if retryable=true, after retry_after_ms.
```

### C2. The irreversible void's safety flow appears only in the instructions, and neither the tool description nor the schema carries it
- **Where:** `ledgerline_void_entry`.
  - Its description is just "Void a posted journal entry."
  - `confirm_token` is optional and described only as "Token confirming the void."
  - `dry_run` defaults to `false`.
- **Why it matters:** because of C1, a Claude Code model probably never sees the two-step rule. Nothing in the tool text tells it:
  - that the void can't be undone;
  - that a dry run must come first;
  - where the token comes from;
  - that the token expires.

  The schema also permits a call with neither `dry_run` nor `confirm_token`, and the description doesn't say what the server does then.
- **Remediation:** repeat the rule in the tool, where it applies at call time:
  - **Description:** "Irreversibly void a posted journal entry. Two steps: (1) call with dry_run=true to get a preview and a confirm_token; show the preview to the accountant; (2) call again with the same project_id and entry_id plus confirm_token, within 5 minutes. Without a valid token the call is refused with `<code>`. An expired token returns `<code>`: repeat step 1."
  - **`confirm_token`:** "Token returned by a dry_run=true call to this tool for the same entry. Expires 5 minutes after issue."
  - **Server side:** reject a non-dry-run call that lacks a token, using a structured error whose `repair` points at the dry-run call. Keep `destructiveHint: true`; it is correct.

## High

### H1. The `project_id` prerequisite and the "names are never IDs" rule are missing from every project-scoped tool
- **Where:** `project_id` in `get_entries`, `post_entry` and `void_entry` is described only as "Project identifier."
- **Why it matters:** project names repeat with year suffixes, so an agent that guesses an identifier from "Acme 2025" will fail or pick the wrong year's books.
- **Remediation:**
  - Describe `project_id` as: "Opaque id from ledgerline_list_projects (not the project name). Names repeat across fiscal years; choose by name and fiscal_year."
  - Have `project_not_found` return a `repair` that points at `ledgerline_list_projects`.

### H2. `ledgerline_post_entry` is not idempotent and has no way to deduplicate, so a retry after a timeout can double-post
- **Where:** `idempotentHint: false`, and the schema has no idempotency key.
- **Why it matters:** in bookkeeping a duplicated entry is a real error that someone has to find and void. Neither the instructions nor the description tell the agent how to recover from an ambiguous failure.
- **Remediation:**
  - Add an optional `idempotency_key` (client-chosen string; a repeat of the same key returns the original entry instead of posting again). Say this in the description.
  - If you can't add one, the description should say: "Not safe to retry blindly: after a timeout or unknown outcome, check ledgerline_get_entries for the entry before posting again."

### H3. The closed-period rule is missing from the write tools and doesn't say which period applies
- **Where:**
  - Rule 3 (instructions only, and truncated) says "check the period_status field of the project first."
  - The `post_entry` and `void_entry` descriptions don't mention periods.
  - `list_projects` mentions only "period status."
- **Ambiguity:** it isn't clear whether period status is one value per project or per accounting period. It also isn't clear what "closed" is checked against: the entry's `date` for posting, or the original entry's date for voiding.
- **Remediation:**
  - In both write tools, add: "Refused with period_closed (non-retryable) if `<the entry date / the voided entry's date>` falls in a closed period; check period_status from ledgerline_list_projects first. On period_closed, stop and ask the accountant; do not pick another date."
  - Document the values `period_status` can take.

### H4. The error-envelope reference uses about 850 characters of the budget on field glossary rather than behaviour
- **Where:** instructions, chars 1,298–2,154.
- **Why it matters:** it describes ten fields, but the only action it prescribes is buried in the `retryable` definition. It is also the part that gets cut off.
- **Remediation:**
  - Replace it with one behavioural rule. The rule in the C1 draft is enough: branch on `code`, follow `repair`, and honour `retryable` / `retry_after_ms`.
  - Move the field glossary to documentation, or to a resource if you expose one. The error objects already describe themselves.

- It sits at char 2,155, so on a truncating client it is itself cut off. A model that does see it can't recover text it never received.

- `date` has no description, and nothing says whether it is the entry's effective date.
- `lines[].account`: it isn't clear whether this is an account id, a code or a name, or where valid values come from. No tool lists accounts.

- No memo or description field is offered. That is probably needed for review by a senior partner.
- **Remediation:**
  - Describe each field.
  - Add `minimum: 0` and a "set exactly one of debit/credit" rule, or restructure each line as `{account, amount, side: "debit"|"credit"}`.
  - State the currency and precision.
  - Say where account identifiers come from, and add a list-accounts tool if they can't be found otherwise.
  - Make sure an unbalanced entry returns a structured error with `field: "lines"`.

### M4. `ledgerline_get_entries` can't serve the stated month-end workflow efficiently
- The workflow described is "reviewing unposted entries," but there is no status filter.
- There is no pagination or `limit`, even though `list_projects` has a cursor. On a busy ledger that means an unbounded response.
- **Remediation:**
  - Add a `status` filter (e.g. `posted` | `unposted` | `void`), a `limit`, and a `cursor`.
  - Say what each returned entry contains, in particular the `entry_id` that `void_entry` needs.
  - Describe `since` more precisely: which date it compares against (entry date or creation date), and that it is inclusive.

### M5. The rate limit is stated as something the agent must count
- "Keep to 30 calls per minute per project" asks the model to meter itself, which it can't do reliably, and the rule is truncated anyway.
- The server already enforces the limit and returns `rate_limited` with `retry_after_ms`.
- **Remediation:** rephrase it as a reaction ("on rate_limited, wait retry_after_ms before retrying"), which the C1 draft's error rule already covers. Keep the number only as information.

## Findings

### F1: The binding rules exist only in `instructions`, and they fall past Claude Code's measured prefix

- **Severity:** Major
- **Section:** §2, §3 (`[2.instructions-advisory]`, `[2.instructions-prefix]`, `[3.constraint-separation]`)
- **Summary:** All four rules start at character 2,208, 160 characters past Claude Code's 2,048-character default cut. None of the four is carried by any tool schema or description, so a Claude Code agent sees none of them.
- **Evidence:**
  - The offset table above.
  - Tool descriptions: "Return journal entries for one project, newest first.", "Post a balanced journal entry to a project.", "Void a posted journal entry."
  - `project_id` is described only as "Project identifier." on all three project-scoped tools.
  - `confirm_token` is described only as "Token confirming the void."
  - No schema or description mentions project-name rejection, the dry-run token flow, its 5-minute expiry, the closed-period ban, or the 30 calls/minute limit.
- **Why not Critical:** the rules imply the server rejects bad calls (names as ids, voids without a token, closed-period writes), so the agent's cost is failed calls rather than bad data. It would become Critical if the server does not enforce `confirm_token` or the closed-period ban server-side, or if a Claude Code transcript shows a void or post going through that the rules forbid.
- **Remediation:**
  - Put each rule on the surface the agent is guaranteed to see: the governing tool's `description` and `inputSchema`. F3, F4 and F7 give the per-tool text.

```
Ledgerline: bookkeeping ledgers for an accountant's client projects. Tools list projects, read and post journal entries, and void entries. It does not file taxes, move money, connect bank accounts, send invoices, or expose invoices in this version.
Truncation check: this text ends with the line "END ledgerline instructions 3.2.0". If your copy does not end with that line, it was cut; every rule below is also stated in the description and inputSchema of the tool it governs, so read those.
Rules:
- Identify a project only by the project_id that ledgerline_list_projects returns; names repeat across fiscal years and are rejected.
- Call ledgerline_post_entry or ledgerline_void_entry only when that project's period_status from ledgerline_list_projects is "open".
- Voiding cannot be undone and takes two calls: ledgerline_void_entry with dry_run=true returns a confirm_token valid for 5 minutes; call it again with that confirm_token to apply the void.
- On any error, branch on code; when retryable is false, do not repeat the same call; when repair is present, make that call.
Context: each client's books are one project; many accountants keep one project per fiscal year. Every error carries request_id; quote it to support.
END ledgerline instructions 3.2.0
```

### F3: The two-step void flow and its token lifetime are invisible in `ledgerline_void_entry`'s schema, and one annotation covers both preview and void

- **Severity:** Major
- **Section:** §3, §1 (`[3.sec-confirmation]`, `[3.required-optional]`, `[3.ap-mode-annotations]`, `[1.state-handles]`)
- **Summary:** Nothing in the tool says the void is irreversible, that `dry_run=true` returns `confirm_token`, or that the token expires in 5 minutes. `confirm_token` is optional in the schema even though a real void requires it. The read-only preview carries `destructiveHint: true`, so the mandatory preview call pays mutation-grade confirmation.
- **Evidence:**
  - `"required": ["project_id","entry_id"]`.
  - `confirm_token`: "Token confirming the void."
  - `dry_run`: "Preview the void without applying it."
  - `annotations: {destructiveHint: true}` covers both modes.
  - The token rule appears only at character 2,381 of `instructions`.
  - No error code for a missing or expired token is documented.
- **Why not Critical:** it would be Critical if a void without a token is not rejected server-side.
- **Remediation (preferred): split the tool.**
  - Add `ledgerline_preview_void(project_id, entry_id)` with `readOnlyHint: true`. It returns `{confirm_token, expires_at, preview}` under an `outputSchema`.
  - Keep `ledgerline_void_entry(project_id, entry_id, confirm_token)`, with `confirm_token` required, `destructiveHint: true`, `idempotentHint: false`.
  - Description: "Irreversibly voids a posted entry. Requires confirm_token from ledgerline_preview_void for the same entry_id; the token expires 5 minutes after issue."
  - Document a stable code for an expired or mismatched token, with `repair` → `ledgerline_preview_void` carrying the same `project_id`/`entry_id`.
- **Remediation (if the tool stays combined):**
  - Document `confirm_token` as "Required when dry_run is false; value of confirm_token from a dry_run=true call on the same entry_id; expires after 5 minutes."
  - State in the description that the annotations describe the whole tool, not the selected mode.

  - `ledgerline_list_projects` mentions "period status" in prose, but no output schema names `period_status` or its values.
  - The closed-period rule appears only at character 2,544 of `instructions`.
- **Remediation:**
  - Describe `project_id` as "Opaque id from ledgerline_list_projects (projects[].project_id). Project names are not accepted."

### F5: No tool publishes an `outputSchema`

- **Severity:** Major
- **Section:** §3 (`[3.output-schema]`, `[3.structured-default]`)
- **Summary:** None of the four tools declares an `outputSchema`. All four return data an agent parses (ids, period status, entries, tokens), so none qualifies for the carve-out.
- **Evidence:**
  - None of the four records has an `outputSchema` key.
  - The binding rules depend on fields no published schema declares: `project_id`, `period_status`, `confirm_token`. Entry ids and the next-page cursor are also undeclared.
- **Remediation:** publish a per-tool `outputSchema` and return `structuredContent`:
  - `ledgerline_list_projects`: `{projects:[{project_id, name, fiscal_year, period_status:"open"|"closed"}], next_cursor}`.
  - `ledgerline_get_entries`: `{entries:[{entry_id, date, status, lines}], has_more, next_cursor, truncated}`.
  - `ledgerline_post_entry`: `{entry_id, status}`.
  - Void or preview: `{entry_id, voided}` / `{confirm_token, expires_at}`.

### F6: The valid values for `ledgerline_post_entry`'s `account` are undiscoverable, and its name is ambiguous

- **Severity:** Major
- **Section:** §3 (`[3.param-names]`, `[6.repair-callable]`)
- **Summary:** `lines[].account` is a bare string with no description. Nothing says whether it is an account id, a code or a name, and no tool enumerates a project's accounts, so the first post has to guess.
- **Evidence:**
  - `"account": {"type": "string"}` has no description.
  - No `list_accounts`-style tool exists.
  - `ledgerline_get_entries` publishes no output shape from which accounts could be learned.
  - The headline task, "correcting miscategorized transactions", depends on choosing the right account.
- **Remediation:**
  - Rename the field to `account_id` (or `account_code`) and describe its form.
  - Add a read-only `ledgerline_list_accounts(project_id, cursor)`.
  - Make a bad-account error carry `field: "lines.account_id"` and `repair` → `ledgerline_list_accounts` with the same `project_id`.

### F7: `ledgerline_post_entry` has no idempotency key and no reconcile path

- **Severity:** Major
- **Section:** §3, §6 (`[3.idempotency-key]`, `[3.dispatched-vs-applied]`)
- **Summary:** An agent that retries after a timeout can post a duplicate journal entry into a client's books. It has no key to deduplicate with, and no documented way to check whether the first post landed.
- **Evidence:**
  - `idempotentHint: false`, which is honest.
  - There is no `idempotency_key` property.
  - `ledgerline_get_entries` filters only by `since`, and the description names no lookup surface.
- **Why not Critical:** it would be Critical if a timeout-then-retry fixture shows duplicate entries.
- **Remediation:**
  - Add an optional `idempotency_key` string: "re-sends with the same key within N minutes return the original entry_id; omit for no deduplication".
  - Return `entry_id` in `structuredContent`.
  - Add an `idempotency_key` or `entry_id` filter to `ledgerline_get_entries`.
  - Name that filter in the description as the way to reconcile after a timeout.

### F8: `ledgerline_get_entries` has no bound, pagination or status filter

- **Severity:** Major
- **Section:** §8, §3 (`[8.detail-row-count]`, `[8.truncation]`, `[8.filters]`, `[3.task-completing]`)
- **Summary:** If `since` is omitted, the tool returns a project's whole entry history, newest first. It declares no cap, cursor or truncation signal. It also can't filter to unposted entries, which the instructions name as the core month-end task.
- **Evidence:**
  - `inputSchema` properties are only `project_id` and `since`.
  - The instructions say "reviewing unposted entries".
  - The finding would drop if the server documents a server-side cap.
- **Remediation:**
  - Add `cursor`.
  - Enforce a server cap with `truncated: true` and a `truncation_hint` naming `since` or `status`.
  - Add `has_more`/`next_cursor` under the `outputSchema`.
  - Add `status: "unposted"|"posted"|"voided"` and an `until` date.
  - Rename `since` to `entry_date_from`, per `[3.param-names]`, and say which date it compares.

### F12: `ledgerline_post_entry`'s input schema is loose

- **Severity:** Minor
- **Section:** §3, §8 (`[3.strict-types]`, `[3.required-optional]`, `[8.locale-independent]`)
- **Summary:**
  - `date` has no description: entry date or posting date, and which period does it land in?
  - `lines` has no `minItems`.
  - `debit` and `credit` are both optional floats, with no rule that exactly one is set.
  - Money is a JSON `number` with no currency or minor units.
- **Evidence:**
  - `"date": {"type":"string","format":"date"}`.
  - `"debit": {"type":"number"}`, `"credit": {"type":"number"}`.
  - `"required": ["account"]` on line items.
- **Remediation:**
  - Use `debit_minor`/`credit_minor` as `integer` minor units, plus a project currency (ISO-4217) exposed from `ledgerline_list_projects`.
  - Describe each line as "set exactly one of debit_minor or credit_minor, > 0".
  - Set `lines.minItems: 2`.
  - Describe `date` as "Entry date (YYYY-MM-DD); determines the period checked against period_status".
  - Make an unbalanced entry fail with `field: "lines"`.

### F15: The error envelope drifts from the unified contract

## Open questions and assumptions

## Remediation summary

Most Major findings share one root cause: the contract lives in prose (`instructions`) rather than in the tool schemas.
1. Move each rule into the governing tool's `description` and `inputSchema` (F1, F3, F4, F7).
2. Publish output schemas (F5).
3. Then shrink and reorder `instructions`, using the draft under F1.
